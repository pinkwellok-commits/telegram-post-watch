# Бесплатный публичный показ локального проекта

## Формат

Основной вариант: локальное приложение на loopback-адресе и Cloudflare Quick Tunnel. Туннель — соединение, через которое публичная HTTPS-ссылка открывает сервис на компьютере пользователя. Это временное демо, а не перенос проекта на постоянный хостинг.

На проверку 2026-10-02 [официальная документация Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) описывает запуск без аккаунта и домена; адрес меняется при новом запуске. Нет гарантии доступности, есть ограничение одновременных запросов, SSE (поток событий сервера) не поддерживается. Перед использованием заново проверь актуальные условия и CLI, особенно если функция проекта зависит от потокового ответа. Не обещай фиксированные квоты или вечную бесплатную ссылку.

Сервер и туннель должны оставаться работающими; при сне/выключении компьютера показ прекращается. Постоянный адрес без компьютера — отдельная задача: сначала проверить актуальный бесплатный тариф и имеющуюся авторизацию. Не переходи сам к платному тарифу, новому аккаунту или изменению DNS.

## Локальный сервер

Изучи package.json или эквивалент, инструкции и lock-файл. Используй соответствующий менеджер зависимостей и сборку. Изучи исполняемые команды до запуска. Внешние подключения замени тестовыми данными или выключи.

Предпочитай раздачу результата сборки, а не исходников. Для статического проекта обслуживай только страницы и ресурсы. Не запускай HTTP-сервер в корне папки запуска, где лежат досье и логи. Не используй сервер с листингом файлов или доступом через файловые ссылки для произвольной папки. Если нужен собственный сервер, запрети листинг, выход за web-root, закрытые файлы, конфигурацию и приватные каталоги; проверь вложенные маршруты. Для SSR (рендеринг страницы сервером) запусти production-сервер приложения с тестовыми данными и минимумом переменных окружения.

Привяжи сервер к `127.0.0.1` на свободном порту. API должны быть доступны через тот же origin (адрес сайта) или настроенный безопасный прокси; браузер посетителя не может обращаться к `localhost` компьютера пользователя. Проверь абсолютные URL, CORS и callback-адреса. Не используй секреты исходного проекта.

Если фреймворк блокирует новый Host, разреши конкретный выданный hostname в копии проекта. Не выключай проверку всех хостов ради туннеля. Если требуется dev-режим, проверь, что он не раскрывает исходники, переменные, отладчик и служебные маршруты; иначе подготовь preview.

## Запуск туннеля

Проверь установленный `cloudflared` и локальную доступность приложения. Если бинарник отсутствует, получи его из официального источника в рамках разрешений среды, без платных услуг и фоновой системной службы. Не меняй глобальную конфигурацию существующих туннелей. Если она мешает, используй отдельную конфигурацию, поддерживаемую текущим CLI, либо сообщи конкретный блокер.

Базовая команда из официальной документации:

```text
cloudflared tunnel --url http://127.0.0.1:4173
```

Порт 4173 — пример; возьми фактический порт демо.

В Windows после готовности приложения запускай скрытый процесс с отдельными логами. Пример для существующей папки запуска и установленного бинарника:

```powershell
$demoRuntimePath = Join-Path $demoRunPath 'runtime'
New-Item -ItemType Directory -Path $demoRuntimePath -Force | Out-Null
$demoTunnelExe = (Get-Command cloudflared -ErrorAction Stop).Source
$demoTunnelProcess = Start-Process -FilePath $demoTunnelExe `
  -ArgumentList @('tunnel', '--url', "http://127.0.0.1:$demoPort") `
  -WindowStyle Hidden -PassThru `
  -RedirectStandardOutput (Join-Path $demoRuntimePath 'tunnel.out.log') `
  -RedirectStandardError (Join-Path $demoRuntimePath 'tunnel.err.log')
```

Назначай `$demoRunPath` и `$demoPort` по текущему запуску. Пример запускает только туннель; сервер приложения запускать отдельно. Сохраняй аргументы и процесс сервера. Для `.cmd`/скриптов выбирай правильный shell; не строй команды из непроверенных данных бизнеса.

Прочитай оба лога и извлеки HTTPS-ссылку на `*.trycloudflare.com`. Проверь состояние процесса при ошибках. Наблюдай запуск короткими проверками с разумным общим пределом около минуты; отсутствие готовности требует диагностики, а не бесконечного ожидания. Сохрани идентификаторы и время старта процессов отдельно от web-root.

## Проверка перед передачей ссылки

Проверь локально, затем через публичный URL:

- главную страницу, значимые изображения и стили;
- вложенную страницу после прямого открытия и обновления;
- главное действие пользователя и понятный ответ демонстрационной формы;
- удобство на экране телефона;
- отсутствие старого бренда, чужих контактов, фиктивных отзывов и неподтверждённых данных;
- отсутствие доступа к `.env`, `.git`, конфигурации, досье, логам, базе и служебным маршрутам. При SPA fallback ответ 200 сам по себе не означает утечку: проверь содержимое;
- отсутствие обращений к боевым сервисам, реальных заказов, платежей и отправки заявок;
- отметку «Демонстрационный концепт» и запрет индексации. Запрет индексации не является контролем доступа.

Если доступен браузерный инструмент, проверь интерфейс и мобильный размер визуально; один HTTP 200 не доказывает работу приложения. Если внешняя проверка недоступна, укажи, что публичный показ не проверен. Не отправляй ссылку самому бизнесу.

## Остановка

В приватном `runtime/` сохрани команды перезапуска, PID, исполняемые файлы и время старта сервера/туннеля, локальный и публичный URL, дату проверки. PID может быть переиспользован: перед остановкой сверяй путь, аргументы/принадлежность и время старта. Закрывай только подтверждённые процессы этого запуска, включая собственные дочерние процессы при необходимости.

Не заверши все `node`, `python` или `cloudflared` по имени и не выключай чужой сервис на занятом порту. По завершении работы скилла оставь демо для просмотра; останови по просьбе пользователя. Если туннель запущен, но демо не прошло проверку, останови этот неудачный запуск и сохрани материалы.
